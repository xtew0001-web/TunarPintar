TUNAIPINTAR PROTOTYPE — IMPLEMENTATION PLAN
===========================================

1. PURPOSE AND PRODUCT STORY
----------------------------
Build a polished assignment prototype that explains how TunaiPintar helps Malaysian
SMEs earn returns on genuinely surplus cash without putting payroll, supplier payments,
or daily operations at risk.

The site must clearly communicate:
- Problem: SME cash often sits idle because owners cannot confidently identify how much
  can be invested without creating a liquidity shortfall.
- Target users: Malaysian SME owners, finance managers, and lean finance teams without a
  dedicated treasury function.
- Value proposition: accounting- and bank-data-aware cash-flow forecasting estimates the
  safe-to-invest amount, maintains a conservative reserve, and proposes automated sweeps.
- Customer benefits: better use of idle cash, preserved operating liquidity, less manual
  treasury work, Shariah or Non-Shariah preferences, and clearer forward visibility.
- Safety position: forecasts, transactions, connections, recommendations, returns, and
  investment actions are simulated. Returns are estimates and are not guaranteed.

Primary user journey:
1. Read the short product explanation on the login screen.
2. Enter any non-empty email and password and choose Shariah or Non-Shariah mode.
3. Arrive at an authenticated-looking dashboard populated from /api/dashboard.
4. Explore cash flow, investments, transactions, reports, integrations, and settings.
5. Review and confirm a simulated sweep, adjust prototype settings, or log out.


2. TECHNICAL ARCHITECTURE
-------------------------
- Backend: Python Flask.
- Frontend: semantic HTML, CSS, and vanilla JavaScript only.
- Data: backend/demo_data.json; no database and no real financial integrations.
- Server: one Flask process serves the frontend files and the JSON API.
- API: GET /api/dashboard reads demo_data.json and returns JSON.
- Frontend routing: hash-based views (#dashboard, #cash-flow, #investments,
  #transactions, #reports, #integrations, #settings) so each sidebar item is a distinct,
  linkable view without adding a frontend framework.
- Demo session: browser sessionStorage only. It is a UI convenience, not authentication.
- Prototype changes: client-side state only. Confirmed sweeps, filter choices, connection
  toggles, reserve changes, and notifications do not move money or modify bank accounts.
- Charts: accessible inline SVG or Canvas generated with vanilla JavaScript; no charting
  dependency is required.
- Failure state: if /api/dashboard fails, show a helpful retry panel instead of an empty or
  broken dashboard.

Planned Flask routes:
- GET /                       -> frontend/index.html
- GET /style.css              -> frontend/style.css
- GET /script.js              -> frontend/script.js
- GET /assets/<path>          -> frontend/assets/<path>
- GET /api/dashboard          -> parsed backend/demo_data.json
- GET /health                 -> small optional health response used during testing

Planned API data groups:
- meta: demo label, currency, generated date, disclaimer
- company: fictional SME name and compliance mode
- balances: total business cash, reserved cash, estimated surplus, invested balance
- cash_flow: historical and forecast monthly/weekly points
- upcoming_expenses: fictional payment schedule
- investment: fictional fund, allocation, indicative return, and proposed sweep
- transactions: fictional deposits, expenses, investments, and redemptions
- reports: monthly cash and simulated performance summaries
- integrations: fictional bank and accounting connection states
- settings: minimum reserve and notification preferences
- insights: simulated AI recommendations and risk notes

Data consistency rules:
- Use RM throughout and format values consistently.
- Total business cash, reserved cash, estimated surplus, invested balance, proposed sweep,
  payments, reports, and transactions must reconcile logically.
- Dates and descriptions must remain consistent between the dashboard, cash-flow schedule,
  transaction table, and reports.
- Every forecast, AI recommendation, transaction, connection, and return figure must carry
  a visible “Demo data” or “Simulated” treatment where users could mistake it for live data.


3. INFORMATION ARCHITECTURE AND PAGE STRUCTURE
----------------------------------------------

A. DEMO LOGIN
- TunaiPintar wordmark and concise value proposition.
- Problem, target customer, and three concrete customer benefits.
- Email and password inputs; accept any non-empty values.
- Shariah / Non-Shariah compliance selector.
- Explicit notice: simulated login, no account security, no real financial access.
- Validation for empty fields and a working sign-in button.

B. SHARED AUTHENTICATED SHELL
- Persistent desktop sidebar with all seven navigation destinations.
- Mobile header and accessible sidebar drawer/menu.
- Company identity, “Demo data” badge, compliance badge, prototype disclaimer, and logout.
- Loading, API error, retry, and success/toast states.

C. DASHBOARD
- Four primary KPI cards: total business cash, reserved cash, estimated surplus cash,
  and invested balance.
- Upcoming expenses summary and short cash-flow forecast chart.
- Recent transactions table/list.
- AI insight panel explaining why a sweep is considered safe and what assumptions matter.
- Concise product-value reminder so the prototype also works as a business showcase.

D. CASH FLOW
- Larger historical + forecast cash chart with legend and simulated-data annotation.
- Forecast confidence/safety-buffer explanation without implying certainty.
- Upcoming payment schedule with date, payee, category, and RM amount.
- View controls (for example 30/60/90 days) that update the display.

E. INVESTMENTS
- Fictional Shariah-compliant money market fund portfolio (or Non-Shariah presentation
  based on the demo login preference).
- Invested amount, indicative annualised return, estimated earned return, liquidity note,
  and risk/disclaimer copy.
- Proposed sweep card showing source cash, reserve requirement, sweep amount, and projected
  post-sweep liquidity.
- Review modal/panel followed by explicit simulated confirmation and success feedback.
- No real investment language and no guaranteed-return claim.

F. TRANSACTIONS
- Fictional records with date, description, type, status, and RM amount.
- Working text search, type filter, status filter, and clear/reset action.
- Responsive desktop table and mobile card presentation.
- Useful no-results state.

G. REPORTS
- Monthly cash summary, investment summary, and simulated performance figures.
- Lightweight comparison chart or bars generated from API data.
- Month tabs/filter that update the displayed summary.
- “Demo report” label and concise interpretation.

H. INTEGRATIONS
- Fictional bank and accounting-software connection cards.
- Simulated connected/disconnected status, last sync time, and sync action.
- Connect/disconnect or resync interaction with confirmation and clear prototype notice.
- No credential collection and no claim of real connectivity.

I. SETTINGS
- Editable minimum cash reserve in RM with sensible validation.
- Notification toggles for sweep proposals, forecast warnings, and weekly summaries.
- Compliance preference display/update where appropriate.
- Save interaction updates client-side UI only and confirms that no server record exists.


4. VISUAL AND RESPONSIVE DIRECTION
----------------------------------
Visual thesis: “calm treasury control” — a crisp B2B financial workspace that makes risk,
liquidity, and next actions understandable at a glance.

- Palette: dark teal #0F766E as the primary brand/action colour, deep ink text, white cards,
  light grey canvas, subtle borders, and restrained semantic colours for warnings/status.
- Typography: clear system sans-serif stack, strong numeric hierarchy, readable body text.
- Components: rounded cards, subtle borders/shadows, compact tags, consistent controls.
- Accessibility: semantic landmarks, labels, visible focus states, keyboard-operable controls,
  adequate colour contrast, reduced-motion respect, and text alternatives for charts.
- Desktop: fixed/persistent sidebar and dense but breathable content grid.
- Tablet/mobile: collapsible navigation, stacked cards, scroll-safe charts, touch-sized buttons,
  and transaction cards or horizontally safe tables with no unintended page overflow.
- Animation: only brief state transitions and feedback; no decorative motion dependency.

7. DEMO LIMITATIONS TO DISCLOSE
-------------------------------
- No real authentication, password protection, user accounts, database, or server session.
- No connection to banks, accounting platforms, payment rails, or investment providers.
- No money is moved and no investment order is created.
- All companies, balances, forecasts, transactions, returns, and AI insights are fictional.
- Forecasts and returns are illustrative, not financial advice, and returns are not guaranteed.
- User changes are temporary client-side prototype state and may reset on refresh/restart.
- The forecasting/AI logic is represented by prepared demo data, not a trained production model.
